# T08 合同准备与审批：实施设计

状态：DESIGN_APPROVED。2026-09-21 用户确认 L 高保真及本业务设计。批准不直接激活数据库/API 或证明生产功能完成。2026-09-21 用户授权继续 R2 下一任务，本轮落实设计和缺失画面的准备。

## 目标与已存在的边界

T07 已形成准确报价接受来源，T05 提供客户、参与方与服务需求确认，T06 提供准确材料引用。当前 Contract 模块只有 OpportunityContractReader 及持久化读取，不能称为合同业务已实现。T08 将两种准备来源汇入同一合同版本、签约前冲突审查及审批流程，并形成可追溯的签署准备后继；整个 R2 的签署核验、合同执行、付款条件及转案目标仍保留，不能因 T08 分批交付被删除。

用户已确认：保留正式报价，也允许准确授权后直接准备合同；只有合同明确要求先到账才阻断转案；案管接收后生成案件，再分类。T08 不新增案件业务类型、不引入模板编辑器、自动电子签或 AI 决策。

## 实现路径裁定

推荐：复用现有 Contract 所有权、命令回执、责任/Outbox、T05/T06 读取和冻结工作卡，在现有模块内增加准确版本与后继责任。

不采用“直接在报价里增加合同字段”：会混淆客户接受与授权准备两种事实。暂不采用新建独立合同平台：会增加导航、客户真源及额外审批配置，超出本轮范围。

## 事实、责任与异常

| 起点 | 提交事实 | 后继与完整性要求 |
|---|---|---|
| 已接受准确报价 | 合同准备来源接续 | 可靠消费现有接受结果；按准确来源幂等创建准备责任；历史接受结果可接续，不能靠人工重复记录接受 |
| 直接准备申请 | 绑定商机、客户确认、服务范围、收费方案及理由的申请 | 有权人收到决定责任；保存草稿不接管原跟进；正式申请接管/等待规则保留原 SLA 及来源 |
| 直接准备决定 | 准确申请的批准或退回 | 批准生成合同准备；退回生成补充申请责任；不得伪造报价或客户接受；授权不能套用到变更后的主体、范围或收费 |
| 合同准备 | 不可变合同版本、模板/条款引用和正文摘要 | 草稿不完成责任；形成版本后有唯一提交审查责任；无文件或生成失败不得显示合同已形成 |
| 提交签约前审查 | 当前版本的目的限定冲突审查 | 保持 PRE_CONTRACT 及 scopeHash；旧冲突结果仅可依照既有准确范围规则引用，不能只读客户级 CLEAR |
| 冲突决定 | 通过、补充或阻断 | 通过进入本版审批；补充交销售新责任并重新审查；阻断不能进入签署，留有权业务处置入口；豁免若既有规则要求，保留独立准确决定，销售不得自行解除 |
| 合同审批 | 本版正文和策略对应的批准/退回 | 全部所需有效决定齐备才生成签署准备后继；退回形成修订责任，不能复用旧批准 |
| 修订 | 引用直接前版的新版本 | 原正文/决定保留；重新计算准备来源、冲突与审批依赖，旧任务不重开 |
| 后继衔接 | 原子本地后继或持久化可靠事件 | 显示已提交及下一责任；异步中不重复提交；失败进入主管/运营异常，不悬空 |

签署准备的创建和页面必须按该阶段完整接口另行接入，不允许先建一张无法办理的 OPEN 任务。T08 完整闭环验收必须包含可用后继或明确可恢复的交付边界；不能拿占位按钮宣称签署功能已完成。

## 输入与版本

- 合同引用同一商机及准确客户/参与方、需求、材料、准备来源；只复用已有 Owner，不另建客户身份。
- 合同内容包括委托主体、事项与范围、费用、付款安排、签署人权限、签字盖章及归档要求；付款条件与“是否先到账才转案”均进入准确版本。
- 文档使用受控已审核模板，不以高保真示例文字充当正式模板。绑定 templateVersion、clauseVersionSet、contentDigest；费用沿用精确金额规则及条件收费表达。
- 客户资料、报价接受来源、直接授权范围或正文变化时，重验本版依赖；已成立的历史接受事实不因单纯当前报价到期被抹除。
- 文件生成与存储需要失败恢复：候选文件尚未确认时不泄露下载入口；引用准确原件及扫描状态，生成重试不多建合同版本。

## 接口、安全与数据合同

实施前核对 schema_contract.py、Contract 既有物理结构、runtime-validation-contract 与上位合同/冲突规范；以具名 R2 合同修订说明双入口、人工签署后继及付款语义的差异，再追加新迁移和生成产物。不得修改已部署 V950/V960。当前不预先宣称新表名、版本号、命令数量已激活。

读写使用当前任职/代办、租户和精确 revision/hash 授权，保留 DENY、数据库当前时间、业务锁→身份锁、同步审计和提交后响应。命令保留幂等与未知结果回执，重复事件不得多建任务。台账只披露有权记录与依赖，冲突结果仅披露完成当前审查所需信息。

等待采用可靠调度而非页面刷新。无合格审批任职、权限撤销、组织变化时保留有权异常处置与期限；不自动把销售变成审批人。提交后当前卡退出或显示结果，继续本人后继/我的待办，不能仍停留在已完成的可提交表单。

## 页面约束与待审内容

L 包直接引用 E/master.css，复用 app-header、today、queue、work-card、context、card-action 和原表单；合同台账复用列表选中后显示详情。每项业务单一主命令，历史及低频条件折叠；决定性费用、付款及签署要求不隐藏。我的待办在卡片上方展开，普通切换不弹重复确认，脏表单才提供继续/保存/放弃。

L 为 24 个审阅状态，不是 24 个产品办理步骤。采用合成内存数据；无真实合同、授权、上传下载、业务 API 或跨角色操作。签署/收款/转案后续画面不在本次批准请求内。模板预览只验证信息层级，正式条款不得据此推导。
