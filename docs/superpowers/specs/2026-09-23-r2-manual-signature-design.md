# R2 下一业务任务：人工签署证据、授权核验与归档

Design-Status: APPROVED

## 与现有任务的衔接

本任务承接已实现的 READY_FOR_SIGNATURE。历史文档将签署运行时称为 T09；用户随后以 T09 名称要求完整补齐合同生成、审查与审批，该补齐包已本地验收。为避免把历史 T09 误当签署已实现，本任务以 R2-SIGN 标识实施项，不改写旧编号，也不把它等同于收款或转案任务。

依据：已确认的 R2 全业务计划、冻结 E 母版及 L/M 合同页面。用户要求缺失高保真先确认；N 已确认并进入实施。2026-09-23 新发现存量文字要求缺少结构化清单，用户已确认销售登记、核验人对照正文的业务方式，N1 仅补充字段高保真。

## 目标与范围

销售从当前已批准合同继续收集人工签字件；有权核验人按准确版本、主体、代表权限、签字盖章及文件完整性进行核验。缺项能补证、内容变化能返回新版本、全部必需签署及归档完成后形成持久化的后续交接。我的待办与合同台账提供相同工作台入口，业务状态不能由台账直接修改。

沿用人工证据路线。电子签服务、新模板编辑器、到账确认、合同执行条件判定、转案审核与建案均不在本任务内。后继执行条件任务尚未实现时，只保存可恢复的交接边界并展示等待原因，不创建不能办理的 OPEN 占位任务，不声称合同已经执行。

## 实施方式与选择

推荐在既有 Contract Owner 内扩展签署工作流，复用材料与审计、回执、任务工厂及 worker。它能保留准确版本和跨角色责任；单独建签署子系统会重复权限与状态模型，扩大本轮范围；仅给合同加“已签署”按钮则缺少证据、核验和补正闭环，不采用。

## 业务规则

1. 仅消费当前合同准确版本的有效 signature_readiness；复验批准、签约前审查、来源、商机状态、参与方及任职权限。存量 readiness 也由可靠后台调度接续，不能依赖首次打开页面。重复交接只创建一次责任；无合格负责人进入原协调与恢复机制，保留期限。
2. 从本版已批准的参与方及签署要求形成明确的必需签署、用印和归档安排。销售核对并确认安排与批准条款一致，不得静默把当前 signature_required=false 全量回填为已完成，也不依据自由文本自动推断应签主体。条款不足以明确要求时返回准备修订，不用核验人的勾选补造合同要求。
3. 材料引用必须准确、已扫描并正式接收；上传和保存草稿不确认签署。签字件通常与未签正文的字节不同：分别保存批准正文摘要与签字材料摘要，并由核验人确认内容对应，不把两个文件 SHA 必须相等当作内容一致的判断。
4. 核验包含批准版本、签署主体与代表权限、本次必需签字盖章及材料完整性。每次结论有任职、时间、依据和说明；核验通过须有完整证据并满足确定性检查，不接受客户端传入“全部满足”替代服务端查询。
5. 缺页、模糊或缺少权限依据走同版本补证。保留原提交、材料和意见，新材料作为新证据版本，再提交授权核验；不得覆盖旧记录。正文、委托主体或批准签署安排变化则回到合同修订，新版本重新审查审批，旧签署核验不得移用。
6. 支持部分签署完成，按必需安排继续剩余责任。必需签署、用印、完整归档全部满足后才显示签署完成；不存在“上传一份文件即全合同已签署”。不新增通用用印管理系统。
7. 销售和核验人按原权限办理；页面不提供越权角色切换。销售提交后展示真实责任和等待原因。核验人作出补证结论后不自动进入销售表单。
8. 保留未保存切换提示、提交锁定、同一幂等键的原回执恢复、撤权清空、过期依据重读、并发版本冲突和审计回滚。实际签署日期与系统记录时间分别保存；不信任客户端时钟确定授权有效期。

## 设计约束与 N 高保真

审阅稿使用现有 workbench.css、ledgerMaster.css、workbenchControls.css、contractControls.css 的逐字节快照（审阅服务不公开产品源码路径），不添加替代样式规则。现有 MyTasksControl、BusinessNavigation、工作台壳为实现落点；静态稿仅映射其结构，不复制模拟导航进入产品。不新增看板、标签页体系、悬浮工具条或第二套按钮样式。

N 提供签署安排、材料提交、扫描中、等待核验、授权核验、同版本补证、变更修订、部分签署、归档、完成交接、未知结果、责任待安排、撤权、台账和只读记录。审阅器切场景只为查看角色状态，不等同于产品角色切换。每一工作卡最多一个主操作，当前信息及历史仍在左侧，当前办理在右侧，窄屏按母版折叠。

## 确认后的任务拆分

| 子任务 | 交付与验收 |
| --- | --- |
| SIGN-01 | 冻结签署安排、状态机与准确版本引用；确定所需具名迁移，保持已有签署事实模型及字段合同一致 |
| SIGN-02 | readiness 消费、存量补接、责任与期限、无负责人恢复；不能重复创建任务 |
| SIGN-03 | 签字件提交、扫描接收、补证及草稿；权限和原回执恢复 |
| SIGN-04 | 授权核验、部分完成、正文变化返回修订及全套版本隔离 |
| SIGN-05 | 完整归档、签署完成及执行条件后继交接；不放行到账、转案或建案 |
| SIGN-06 | 接共用工作台、我的待办及合同台账，N 全状态映射与窄屏验收 |
| SIGN-07 | 两个合同来源、旧 readiness、补证、修订、撤权、并发、回滚及真实浏览器全链验收 |

## 验收边界

合成签字件只验证产品流程，不作为真实法律签署。正式签署要求以业务审核后的合同与授权配置为准。R1 PAUSED / R2 NOT_GRANTED 保持；本稿确认不等于生产业务或发布验收。完成以上任务后更新事实证据，不能沿用上一任务测试数量作为签署验收结果。

## 2026-09-23 已确认补充

允许销售在核对安排卡内按准确批准正文登记主体、签字/用印方式、必需项及条款依据。授权核验人必须确认登记完整且符合批准正文；销售登记不是新的合同批准。若仅登记不准确而正文未变，退回补正安排并重新核验，新安排摘要不得沿用旧完成结论。若批准正文或主体改变，仍走合同修订。N1 为新增字段布局补充，用户已于 2026-09-23 确认；不得借此扩大电子签或其他后续任务范围。
