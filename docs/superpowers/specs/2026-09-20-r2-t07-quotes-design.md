# T07 收费方案与报价：业务及设计补充

状态：DESIGN_APPROVED。用户已确认 K2；实施规则见 `docs/baseline/R2-QUOTE-PACKAGE-V1.md`。不据此宣称产品功能已完成。

## 范围依据

承接已确认的 R2 完整销售 MVP 计划中 R2-3“材料接收＋收费/报价及客户确认”。现有 T05 文档明确 T07/T08 消费准确客户、需求及服务范围。本次将 T07 映射为报价闭环；直接准备合同的具名授权和合同制作由后续工作包实施，两入口最终汇合。不得以本任务为由删除直接授权路径，也不把它塞入报价流程产生假报价接受。

功能目标：同一条线索形成的商机，在确认客户资料和接收材料之后，销售能够准备收费方案、形成准确报价版本，提交有权审批、人工交付留证，并记录客户四态回复。所有状态有后继责任或合法结束路径；不能只有一张可保存表单。

## 业务事实与后继责任

| 当前事项 | 提交结果 | 原责任 | 后继责任 |
|---|---|---|---|
| 准备收费方案 | 确认准确 QuoteRevision，连同范围、计价行、付款条款原子写入 | 完成准确的准备责任 | 需审批时生成提交审批责任；权限内满足授权规则时进入交付责任 |
| 提交报价审批 | QuoteApprovalRequested，绑定客户需求版本、主体集合、报价哈希、审批策略版本 | 原提交任务完成 | 唯一有权审批人或明确多签审批集合收到各自待办；销售看到审批中 |
| 审批决定 | 对本版作出批准或退回决定 | 本人审批责任完成 | 全部有效批准齐备生成交付责任；退回生成销售修订责任 |
| 修订报价 | 新版引用直接前版，旧版不变 | 本次修订责任完成 | 重新判定本版授权，旧批准不可套用 |
| 人工交付留证 | 准确报价、接收人、方式、时间、证据的交付事实 | 交付任务完成 | 销售收到客户回复跟进责任 |
| 客户接受 | ACCEPTED + 准确交付版本及证据 | 本次回复责任完成 | 输出可追溯的合同准备来源及可靠后继事件；合同准备仍需对应后续工作包落地 |
| 暂不接受 | NOT_ACCEPTED + 说明及约定时间 | 本次回复责任完成 | 新销售跟进责任 WAITING，可靠调度到期恢复 |
| 明确拒绝 | REJECTED + 原意及证据 | 本次回复责任完成 | 销售处置责任，选择新版本继续沟通或既有 T04 结束流程，不能自动失单 |
| 回复不明确 | AMBIGUOUS + 原意及证据 | 本次回复责任完成 | 核实回复的新责任，明确下一次行动时间，不产生接受事实 |
| 报价过期 | 过期状态及版本不可再新交付/接受 | 不冒充客户拒绝 | 销售决定修订或结束；历史已发生的合法接受不可被当前时间抹除 |
| 任职失效或无审批人 | 有界责任异常 | 不伪造审批完成 | 主管或运营侧看到待修复事项，修复后继续原因果链 |

权限内批准与需审批路径必须由具名策略判断，不使用前端金额推断授权。旧规格的“执行类优惠分档”不能强迫用户在报价前选择执行业务；已确认的案件形成后分类规则优先。实现前以具名策略修订确定适用于统一销售入口的审批矩阵，K 稿展示需审批路径，不擅自给出新的折扣阈值。

## 与 T01～T06 的衔接

1. 复用原 Opportunity 和 T05 准确客户确认，不新建第二套客户、主体或需求真源。未确认主体/范围时指向已有维护入口；修改形成新版，不静默替换报价引用。
2. 复用 T06 材料原件及准确版本作为交付和客户回复证据；上传、扫描通过或接收材料不等于报价交付、客户接受、合同签署或到账。
3. 保存报价草稿不完成普通跟进，不提前唤醒 WAITING 或重置 SLA。正式进入报价的命令必须明确原跟进如何交接，不留下两张互相冲突的责任。
4. 销售、审批人分别通过自己的任职和待办办理。管理页展示授权范围内当前责任、时间、版本、退回原因及下一行动。
5. 成功后明确展示已完成事项与下一责任。本人可办理时提供继续入口，交给其他人时显示负责人和进展入口；保留系统推荐和“我的待办”主动切换，不伪造他人权限。
6. 同步未完成显示“结果已记录，后继正在同步”；失败进入异常处置，不让销售再次提交已完成操作。
7. 商机已结束、失权、负责人变化、主体依据变化和报价过期都必须重验。旧任务不重开，旧版本不覆盖。

## 输入与准确性

- 收费方案包含服务范围、多项计价明细、币种、费用条件、折扣明细、付款安排及有效期。金额以最小货币单位计算，明细与合计一致，禁止浮点误差、溢出或不明确的负总额。条件性收费明确计算依据、触发条件及上限，不能把尚不确定费用伪装为已定金额。
- 页面默认显示必要输入，更多计价行、折扣及付款条款按需展开；核对步骤完整展示，不能隐去决定性条款。
- 报价文件与报价内容绑定准确版本；提供有权下载，不把点击下载当作已交付。首版交付路径采用 R2 已允许的“经确认人工交付留证”，不做供应商发送平台。
- 人工交付是对已发生交付的确认：接收人、方式、实际时间、准确证明版本必需。需对旧 QuoteIssued 仅允许供应商权威确认的规则作具名修订；保留可追溯来源类型，不能伪造供应商回调。
- 客户四态回复沿用现有枚举 ACCEPTED / NOT_ACCEPTED / REJECTED / AMBIGUOUS。默认不选“接受”，无证据不推进合同准备；例稿预填仅用于视觉审阅。
- 所有有副作用命令绑定任职、对象、准确版本、前置事实、幂等键与摘要。双击、重试、并发和乱序不多建报价、决定或任务。未知结果只查原回执，不换键重发。

## 页面与母版约束

K 稿直接链接 `../2026-09-14-e/master.css`，不复制或修改母版，不新增产品 CSS。台账沿用 G 的列表＋详情；办理页沿用 E 的左侧依据＋右侧单目的表单；T05/I2 与 T06/J 入口原样复用。默认只有一张完整工作卡和一个视觉主操作，历史及低频信息按需展开。审阅工具的场景/画幅选择不属于产品导航。

K 稿覆盖 35 个正常、退回、等待、异常、权限和只读场景；收费与条件性计价细化须在最终高保真中可核对。合同准备入口在稿中仅展示衔接说明，不冒充已经落地的合同功能。

## 不在本任务范围

合同模板生成、直接准备合同授权的完整实施、冲突审查、签署、付款确认、转案、案件分类、AI、外部自动发送、独立报价门户和复杂审批流程编辑器。保留它们在 R2 总计划的后续任务，不将其删除或暗中提前实现。

## 验收要求

逐条验证：线索有效首联→客户确认→材料→报价准备→审批→人工交付→四态回复；退回新版本；权限内与需审批；多签未齐；无审批人；等待到期；旧报价过期；主体或负责人变化；旧批准/证据不可挪用；结束后只读；重复和结果未知恢复；跨租户拒绝；当前待办与台账一致。完整合同闭环由后续合同任务集成后再验收，T07 不以“接受已记录”宣称合同已实现。
