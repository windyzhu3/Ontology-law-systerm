每条链逐节点验收：

1. 销售录入或导入 → 主管去重/补齐/分配 → 对应销售首联，核对原来源、责任及期限。
2. 有效联系形成唯一商机 → 完成当事方、客户需求及材料 → 报价或直接合同入口。
3. 销售形成报价 → 主管批准 → 销售记录真实模拟交付及客户回复；仅下载不是交付，仅批准不是接受。
4. 销售准备/生成/人工确认合同准确版本 → 案管审查 → 主管批准 → 销售签署安排和收集 → 案管核验、归档。
5. 销售提交凭据、财务独立确认；先款与非先款各按原条件推进，不能统一改成先款。
6. 销售执行条件核对、转案提交 → 案管审查/退回/接收 → 唯一案件 → 分类与承接；分类更正保持 Matter ID。
7. 每个节点检查前后任务、数量、授权、历史、材料版本、原回执；无重复后继、无失踪责任，无旧卡覆盖。

主链关闭时，G01—G05 应有 **5 个不同已接收案件**，每条链一个。以明确 ID 集合核对，不把初始化夹具或后续分支算进去。非先款链在完成主链时允许仍有合法财务责任；它不构成失败，也不能为了清空待办虚报到账。

## 9. 恢复、后台、容量与性能

1. **未知结果恢复：** 保存/确认响应丢失、浏览器刷新、关闭后重登录；凭原 commandId/receipt 恢复，不用新键重做。至少覆盖导入、合同、财务、接收各一个实际场景。
2. **后台接续：** UI 关闭后等待仍能恢复；Worker 重启、旧游标、失权、无变化反复扫描；检查无重复任务/审计噪声、无旧报价责任在合同接管后复活。
3. **真实并发：** 两销售同时操作各自业务、主管同时审批、财务/案管同时办理；对同一版本并发提交只允许准确的一次结果。
4. **数据恢复：** E1 和 G 主链完成后分别备份业务库、身份、材料、密钥引用、制品及配置；在另一恢复实例校验登录、任务、材料摘要、回执和唯一案件。不能只恢复 SQL 库就宣告恢复通过。
5. **性能专用轮次：** 从 E1 独立派生性能实例，经真实命令准备 100 合同背景、20 条以上待办，避免污染业务验收计数；记录 CPU/内存/连接池、冷/热态、Worker 健康和确切数据规模。
6. **继承门槛：** 5 并发、至少 100 次：热当前责任 API P95 ≤2 秒；选卡到可操作 P95 ≤1 秒；合同列表首屏 20 行 API P95 ≤2 秒、页面可操作 P95 ≤3 秒。新等待列表/详情另建议热 API P95 ≤2 秒；所有指标记录测量入口，不把 HTTP200 当页面就绪。
7. **持续运行：** 计划增加 60 分钟受控持续负载，观察失败率、连接占用、内存、Worker 与待处理通知增量。既有 R2 通知未消费的边界原样报告，不删通知或改成已投递制造通过。

现有性能记录表明主机容量会影响结果。测试前记录本机实际容量；若门槛未达，报告原值和瓶颈，不在事后降低阈值或只挑最好的一次。
