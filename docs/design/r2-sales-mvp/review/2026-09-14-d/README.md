## 不变的业务与设计约束

- 使用C包原CSS基准：管理侧栏、列表/详情、单卡、原颜色/字体/6px圆角、一个主要操作；没有新增后台平台或导航层级。
- 首次责任尚未存在时不能显示“旧事项已交接”。成功承接后按业务日历起算首次期限；原商机创建时间不作为补计SLA起点。
- 已有责任交接产生准确的新承接关系；旧责任保留“已交接”语义，不伪造业务完成。原截止时间、逾期记录和未来约定时间保留。
- 原始Opportunity形成Owner/Assignment与R1联系来源不可改写。页面的“接手人”指当前责任承担者，不是直接覆盖不可变商机Owner字段。正式实现须具名扩展责任承接合同。
- 原负责人草稿只能作为有权历史参考，不能复制后直接确认为新负责人提交；旧授权、草稿和原请求不能错用。
- 恢复权限与查看权限分开；候选需当前有效人类任职、业务资格及准确对象权限。读取、确认和重放均由服务重验，不能默认换人。
- 原事项已完成/已交接、商机已关闭或提交依据变化时禁止旧输入继续写入，刷新并展示当前结果。原请求结果未知期间不得生成新交接命令。
- 无合格候选仍是未解决异常；协调记录不是业务交接结果。零个或多个主管不能任意选一个；有权运营只看异常编号、授权组织范围、类型和发现/核对记录，不披露客户正文。
- 工作卡视角切换仅为审阅。正式应用以当前任职授权展示，主管不能借此代办。
- 报价及授权直接合同、人工签署、按合同首款约定、案管接收后建案再分类均不变。AI仍限三项人工确认辅助，本包不增加AI决策。

## 确认后的实施顺序

1. 有界发现无效负责人的真实异常，持久记录与去重；不能继续以“可执行候选为空”掩盖无法承接的业务。
2. 接入有权主管的异常查询、候选资格查询及运营受限摘要，明确独立读取/处置权限。
3. 实现具名交接/协调命令、原子责任承接、审计回执、准确版本与同键恢复；保证原来源不变、未来等待不提前、旧草稿不复用。
4. 按本包接入管理页，与我的待办及后台检查点联通，验证多角色异常恢复后业务继续执行，再启用生产调度装配。
