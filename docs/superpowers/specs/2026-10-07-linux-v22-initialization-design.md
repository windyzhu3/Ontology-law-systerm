# Linux v20→v22 发布与海华首次初始化设计

状态：用户已于2026-10-07确认；实施计划已确认，按计划实施中；现有环境未执行迁移。日期：2026-10-07。

## 1. 目标、依据与成功标准

用户要求新增 Linux 发布入口，补齐真实 v20→v22 迁移发布，把已确认的初始化配置纳入仓库，完成 Linux 初始化脚本和必要应用调整，并在独立空库验证。环境用于腾讯云 Linux 上线验收；本次不收集或连接云服务器。保留现有本地海华验收库、用户、授权、材料、进程和恢复记录。

已确认的业务输入包括总所及六个平级部门、17名实名账号、任职授权、主任全所业务及身份管理与审计查询、独立线索分配权限、固定日常经办人、来源随实际导入账号自动记录、最低8位与首次改密、三类待审核合同候选。没有历史数据，不预置业务交易。

验收同时要求：

1. 从真实 v20 库执行 V1070、V1080；旧迁移字节及历史前缀不变，旧业务、身份、任务、审计等原事实保留。
2. 从空业务库迁移至 v22，建立实名账号、组织、岗位、任职、明确授权与配置；业务交易数量为零。
3. Linux 上的发布、首次初始化、原键恢复、备份恢复均有可复查结果。缺校验、版本不一致或结果未知时不得开放业务入口。
4. 真实 OIDC 首次改密、两位管理员、来源自动绑定、固定经办人和越权反例通过；空库迁移成功不能替代这些运行验收。
5. 所有代码、公开配置、模板候选和验证说明进入版本控制；秘密、运行日志中的敏感正文、数据库备份和令牌保持在仓库外。

## 3. 方案选择与范围

选择“独立 Linux 控制器，复用冻结的 Flyway、发布状态和领域命令”。另外两种方案不采用：把 Windows 工具机械移植会携带合成账号及本机假设；编写直接灌库的一次性 SQL 会绕过身份管理回执、审计与独立核验。

Linux 控制器提供明确命令：检查候选发布、空库准备、初始化执行、初始化结果核对、v20升级执行、升级状态核对、原尝试恢复、检查点恢复。同版本字节发布与跨版本迁移使用不同入口和日志；普通字节发布继续拒绝 schema 差异。

保留一个 SPA、一份 OpenAPI、同一 JAR 的互斥 api/worker、独立身份库及业务库。Flyway 独占 DDL；不修改旧迁移、不新增通用工作流、规则DSL或模板编辑器。不把本次 Linux 工具验收提升为全系统发布准入或真实业务合同审批通过。

## 4. 发布制品与 Linux 边界

新增 deploy/linux，含发布控制器、首次初始化控制器、Linux服务/容器装配、公开配置校验器及操作文档。采用现有 PostgreSQL18、Flyway13.4.0、Keycloak、Java/Node 的锁定版本和镜像摘要；没有另行升级依赖的任务。

发布包冻结 JAR、SPA、API/Worker 启动配置模板、schema manifest、完整迁移目录及逐文件摘要、源提交和必要工具锁。包检查必须验证 JAR/SPA 与其声明的 schema 来源一致，不接受“只把配置版本改成 v22”的包。运行配置、证书及秘密引用另行装配，不写入发布包。

Linux 使用明确运行目录、权限受限的秘密文件和运行日志，拒绝链接逃逸、路径遍历及同名覆盖。DB 使用 TLS 校验和独立迁移 Owner；应用四类角色保持既有最小权限。身份库与业务库保持独立。云域名、证书、网络及凭据由执行时参数提供，本次不向用户索取。

私密参数通过受保护文件或交互输入提供，不能经进程参数、日志、错误正文、生成公开配置或 Git 暴露。初始化原密码使用用户已给出的操作输入，仓库不保存其值。文件持久化采用原子替换；修改前验证操作者权限和运行目录归属。

## 5. v20→v22 迁移发布

### 5.1 前置与检查点

读取并冻结旧部署 gate 的完整值、旧发布摘要、旧 manifest、逐项 Flyway history、当前配置及可执行制品。当前数据库必须准确为 v20；不接受 BLOCKED 的未知失败现场、伪装的 v20、v21 冒充 v20，或未经核对的旧包。v21 只能由同一已登记升级的显式恢复入口处理。

验证旧41份迁移与历史记录一致，新包只能追加准确 V1070、V1080。普通发布入口不能据此自动转换成迁移发布。

对准确旧 gate CAS 进入 MAINTENANCE，关闭业务入口并停止 api/worker 及其他具名业务写入者；验证实际停止和数据库活动，不能仅写一个停止意图。记录维护后的准确 gate。随后在禁止写入期间生成业务库、身份库、材料对象、密钥引用、配置及旧制品的检查点，计算并验证摘要。检查点在另一隔离目标执行恢复核对后，方可推进迁移。备份失败保留维护现场和原日志。

### 5.2 执行与激活

运行日志先记录不可变的升级ID、检查点、旧/新摘要、预期迁移和状态，再产生副作用。运行目录互斥与数据库 gate CAS 共同防止并行升级。

使用锁定 Flyway 和迁移 Owner 执行 validate → migrate → validate。V1070 的真实建表/回填/外键与 V1080 注释必须实际存在；不得执行 Flyway repair、修改历史记录或跳过检查。每步都读取真实 history 与 gate 判定状态；不把进程成功退出当作完整发布成功。

校验旧 history 前缀及所有原事实表的稳定行摘要。允许的差异仅为新增 appointment_role 及其已定义回填、已定义对象约束/注释、两条迁移历史和部署技术状态推进；既有 appointment、authority_grant、业务、任务和审计原行均不改写。schema 验证覆盖新增外键、约束、触发器、权限及 manifest，而非版本字符串比较。

配置和制品切换必须明确绑定验证过的 v22 gate、JAR/SPA/manifest 和运行配置摘要。按观测到的准确 gate CAS 登记新发布；正常 v20→v22 中两份迁移会各自推进 revision，不猜测或覆盖 revision。

业务入口持续关闭。在内部受控入口启动新 API/Worker，按发布门禁完成激活与 TLS/数据库/身份/材料/扫描及 Worker 健康核验，再开放公共入口。失败时 CAS 保持或恢复 BLOCKED/MAINTENANCE，停止新写入，不自动重放业务命令。

### 5.3 中断与恢复

日志阶段区分：维护中、检查点已验证、迁移结果待核对、schema已验证、制品已安装、运行已验证、入口已开放。每个阶段都绑定实际摘要与 gate，不接受操作者手改日志制造完成状态。

结果未知时先核对同一升级的历史、数据库和已安装字节。完全未迁移且旧字节仍匹配时，可明确恢复原 v20 运行。V1070 已提交则数据库为 v21，不能重跑新升级或仅恢复 v20 JAR；同一原尝试可在真实 history/摘要匹配后推进 V1080，再完成后续发布。两步已提交则只恢复安装/验证阶段。

需要回到 v20 时，必须显式恢复已验证的数据库、身份、材料/密钥配置及旧制品检查点，先在隔离目标验证。正常工具不提供数据库向下迁移，不执行 Flyway clean 或旧 JAR 单独回滚。检查点恢复后的入口重新验收；不宣称能保留检查点之后已发生的业务写入。

## 6. 新空库初始化与可重复核对

首次初始化是独立流程，不通过升级入口判断“没找到库就初始化”。必须确认业务目标为空、身份 realm 不存在、运行目录未被其他环境占用。存在旧数据或已有未知日志即停止，绝不清库重来。

顺序为：独立库/角色和TLS前置 → 全量43份Flyway迁移与schema校验 → IdP realm及17个账号 → 当前引导合同建立唯一初始管理员和总所 → 经真实管理命令建立岗位、六部门、人员、任职、第二管理员和显式授权 → 受控业务配置 → 完整核对。

每项创建前持久化原命令ID、准确正文摘要与结果核对位置。网络响应丢失后重读同一回执，或按原键重放原正文；不能生成新键、用名称碰撞认领他人对象或重置密码。执行和核对拆开；核对命令只读。改动配置后不能沿用旧初始化日志，须给出独立具名变更，不能悄悄补授权。

人类身份管理使用现有真实认证和领域命令，不用 SERVICE 冒充管理员，也不通过 SQL 直灌 HUMAN 权限。两位管理员分别完成首次改密后，由操作者提供受保护的本人会话令牌供初始化控制器调用；脚本验证任职和权限。其他15人保持首次改密要求，脚本不代替他们修改密码。此交互阶段须在 Linux 文档中明确，不能宣传为无人工认证的一键初始化。

初始引导固定 IDENTITY_ADMIN 语义保留。丁启明的引导任职用于建立黄雪雪的总所主任任职及四项管理权限；黄雪雪再为丁启明建立主任业务任职并授权，遵守自我授权禁止、最后管理员保护和 DIRECT本人管理。SERVICE 岗位、任职和系统恢复权限使用具名受控运行准备边界，不混入人类“全部业务权限”。

最低密码长度按本环境配置8，保留 notUsername/notEmail；临时密码和 UPDATE_PASSWORD 必须真实生效。未改密不得获得正常业务会话；不启用 directAccessGrant 来绕过浏览器登录。

## 8. 来源自动绑定与责任路由

### 8.1 来源

新增具名 HUMAN 导入来源绑定，运行配置绑定 tenant + principal UUID 与现有受信 source account；逻辑账号在初始化时通过真实 IdP subject/业务principal解析为准确身份。来源仍是现有不可变业务字段，不新增通用来源表或让客户输入 username 充当认证。

人类手工捕获和批量导入只获取本人来源；UI移除选择控件并展示当前来源。服务器在读取和最终提交时按实际认证 actor 再核对绑定，篡改他人 sourceAccountCode 必须拒绝。用户切换任职、账号、重试或刷新不得把旧草稿归给新账号。本人多个任职仅决定合法scope，不允许任意换来源；来源与后续被分配的销售责任人分开。

SERVICE 来源绑定保留现有 mTLS/注册语义，不推断成某个人类账号。已存在导入键和旧原回执重放保持同来源、同正文和既有幂等规则；不得追写旧线索来源。具名配置启用前，旧来源模式保持原行为；启用后不允许回退为用户选择来源。所有变更同步更新 HTTP/OpenAPI 说明及有界反例。

### 8.2 经办人

新增受信的有界责任配置，键为 tenant + 业务来源组织 + 已有固定阶段/权限代码，值为准确任职UUID。配置不能赋权、增加责任阶段或充当完成事实。

日常审批：一部万和峰、二部耿唐琪；核款：一部孙荣慧、二部焦玮琦；合同审查、签署核验归档、转案审查接收分类：杨胜。现有报价/合同审批策略表继续表达审批成员及版本，初始化仅写受控配置事实，不能写审批完成结论。

新责任先按具名策略确定目标，再完整验证该任职有效、获权、组织隶属及独立核验要求。主任全权、陈路监督和其他候选不能使日常目标变成“随便取第一个”。已有仍有效的责任人和准确已冻结审批成员保留，部署配置不能改派旧Task。目标撤权、停任、独立性冲突或配置缺失时进入既有具名异常/等待及恢复链，不能自动转给主任。缺配置环境沿用原唯一候选语义，避免破坏已有实例。

主任必须通过现有合法责任接管/审批成员或本人具备资格的责任办理，不提供越过TaskOwner、替别人完成卡或把根任职直接认作案管归属的“管理员万能按钮”。

## 9. 模板候选纳入仓库
