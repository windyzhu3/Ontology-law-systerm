# R2 商机进展前端办理能力 V1

范围沿用已批准高保真 C 的商机进展场景，不新增页面、业务分类、管理配置或自动 AI 操作。

## 已实现

- `OpportunityProgressForm` 复用原 `form-field` / `form-hint` 和原卡片容器，只显示有效进展类型、进展摘要、下一次跟进时间。提交按钮、保存状态和事项切换由现有单卡壳统一承接，不在字段组件中复制。
- 候选构造严格限制四个接口字段；五类有效交流以外的类型、额外分类字段、非法文本和时间拒绝。发生时间由办理上下文提供，不在表单中生成或自动刷新。下一次时间按设备本地时区输入，转换为 UTC；设备时区明示，不改变后端按来源政策计算 SLA 的时区规则。
- 正式确认只使用当前可编辑草稿的准确 ID、修订、摘要和相同业务值；修改后必须重新保存，已到期的下一次跟进不能直接确认。读取历史草稿不依赖当前时钟，避免过期时间导致整个草稿无法读取。
- `createWorkbenchApi.opportunityWrite` 使用上一批两条专用 HTTP 路由，保留原七类 R1 的请求类型和路由。只允许本人任职，要求准确 Task / Draft 前置条件。
- 连续保存补记：草稿创建 201 与已有草稿更新 200 均接受；时间比较按与 Java Instant 一致的规范表示进行，保留微秒精度，避免设备生成的 .000Z 被误判为内容变化。
- 商机、线索和身份写入共用一个 RecoveryStore。结果未定时不允许另一请求覆盖，完整原请求仅留在内存；sessionStorage 继续只存命令 ID、命令类型、Actor scope 和记录时间四字段。
- 成功响应必须匹配原命令和进展事实类型；草稿还须匹配正文、回执修订及 ETag。格式不符时保留恢复标记；会话失效后的响应不能清除标记。
- 原恢复页显示“记录商机进展”，使用同一个 GET 回执入口；确认后按原流程只读刷新当前责任，不重放业务写入。

## 本批边界与后续接线

字段组件尚未挂入生产 CurrentCard；现有 workcard schema、查询披露和候选选择仍限于 R1，商机事项继续隐藏。下一片需完成准确 Opportunity subject 的授权披露、独立传输增量及解析，再把本批组件/适配器接入原单卡保存、确认、dirty / pending 保护。不得将 Opportunity 伪装为 Lead，或仅删除查询过滤就发放卡片。

生产初始责任激活、可靠到期唤醒仍需完成；本批没有改变 WAITING 状态或加入浏览器唤醒。报价/授权直接合同、签署、按合同条件付款、案管审核接收后建案再分类的既定顺序保持。

## 验证

新增候选、组件、传输和恢复页测试；相关八组前端回归 108 项通过，TypeScript 7.0.2 类型检查通过。包含 R1 表单、我的待办切换、会话/恢复存储兼容，以及错误事实、草稿篡改、丢响应、原请求重试和跨业务未决写入阻断。

Playwright 使用合成数据将实际字段组件放入原卡片样式容器，检查 1440 和 360 像素宽度。截图在 `output/r2-progress-fields-desktop.png` 与 `output/r2-progress-fields-mobile.png`，360 宽度的 document scrollWidth 也是 360。检查用 HTML 留在 output，开发根目录临时入口已删除；这是组件级视觉证据，不是生产办理端到端证据。
