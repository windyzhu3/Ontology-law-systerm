# 销售主导待办管理 MVP：现状评估与下一阶段实施计划

> 阶段范围已被[已确认的 R2 完整销售 MVP 计划](2026-09-13-r2-complete-sales-mvp-plan.md)替代。本文保留历史评估；后续开发以新计划的完整销售闭环、管理能力、AI 范围及设计约束为准，不再沿用本文的 R2/R3 拆分。

> For agentic workers: 实施时按具名业务切片逐项执行；适用 superpowers:executing-plans。本文是阶段计划建议稿，不是已批准的新接口合同，也不是实施完成记录。后续切片分别细化，不先编写整套系统的逐行实现计划。

**Goal:** 让销售通过统一待办流程完成线索导入、商机推进、报价、合同生成和签署，最终转为带唯一稳定 MatterRef 的案件；案件形成后才区分综法、执行或其他业务。主管能够查看当前责任、阻塞和经营台账。

**Architecture:** 复用一个 SPA、一份 OpenAPI、一个 Spring Boot 模块化单体和 api/worker 两种角色；保留领域事实、唯一责任、CommandRuntime、jOOQ、PostgreSQL、审计和幂等机制。按业务切片扩展静态能力，不建设通用流程平台。

**Tech Stack:** 以当前 package-lock.json、backend/pom.xml 和部署锁定版本为准。本次不建议升级技术栈。

**Spec:** 当前依据为 docs/baseline/CURRENT-MVP-BASELINE.md、52＋2 字段合同及 runtime-validation-contract.md。涉及开发准入、导入渠道、管理查询和 R2/R3 新命令的变化，应在对应切片中一次性形成具名后继合同。

**审计基点:** 2026-09-13，本地 main，f2b4795af769a24768ff4630252edf5a01f749dc。审计前工作树无未提交改动。origin 与用户提供仓库一致；git ls-remote 因 GitHub 443 连接失败未取得远端 main，网页读取内容也明显滞后，故不声称已经确认远端与本地完全一致。

## 1. 结论和优先级

当前是“工程底座与 R1 首联切片已有较多实现，完整销售业务应用尚处早期”。下一步应启动 R2 业务开发，先打通 **OpportunityOpened → 销售商机推进待办**，并补充线索导入与最小业务管理查询；随后完成报价、合同签署和转案。用户已明确：销售阶段不按综法、执行等业务类型分流，分类在转为案件之后进行。

按本次用户指示，R1 总验收暂停，不再成为独立业务开发的串行前置。保留其未通过、未执行和用户延期记录；不把暂停解释成验收通过。旧基线第 r1-r2-r3-gates 节仍有硬前置，因此首个实施切片应同步修改该开发排序及其验证器，不靠删测试、伪造台账晋级或无限追加豁免绕过。

三个可选方向：

| 方向 | 收益 | 代价 | 建议 |
|---|---|---|---|
| 按销售业务纵向切片，同时补最低管理能力 | 每阶段出现可用结果，尽快形成合同与转案闭环 | 要协调前后端和多个事实 Owner | **采用** |
| 先建全面 CRM、运营后台和案件管理菜单 | 管理界面数量增长快 | 首联到成交仍可能中断，且引入更多领域范围 | 暂缓 |
| 先收完全部 R1/平台验收，再建设 R2 | 发布证据完整后才扩展 | 延续当前阻塞，业务价值继续推迟 | 不采用本阶段排序 |

## 5. MVP 范围和不可省略的业务事实

按用户本次补充，先以一个试点律所、一套统一销售流程、一套可用的已审核委托合同模板和一个报价交付渠道实施；保持现有租户隔离。**不要求在线索、商机或签约前选择综法/执行/其他业务类型，不先建设按类型分流的销售流程。** 委托主体、拟委托事项、服务范围、费用和签署要求仍需在签约前明确；“分类后置”不等于合同内容可以缺失。模板按已确认条款填充，案管业务类型不作为生成合同的前置字段。

```text
线索录入/导入 → 去重/补齐/分配 → 首联有效 → 商机推进
→ 报价准备/审批 → 准确报价发出及客户回复
→ 签约前冲突审查 → 合同生成/审批 → 签署及合同执行
→ 转案准备（合同约定的生效/到账条件单独核验）
→ 转案快照 → 转案前独立冲突审查 → 案管接收或退回
→ 补正后新快照重提 → 原子接收 + 唯一 MatterRef + 销售回执
→ 案管分类待办 → 综法 / 执行 / 其他 → 对应后续办理责任
```

- 销售主导需求、材料、报价和推进；主管/审批人、冲突审查人、财务、案管分别确认各自负责的事实。
- 下载报价文件不等于已送达，上传签字件不等于签署核验，销售填写“已付款”不等于到账，合同生成不等于合同执行，单笔付款不等于激活，点击接收不等于已经建案。
- MVP 可先采用有证据的人工签署、财务人工核验；不要求同时对接电子签、银行、短信和企业微信。各渠道必须有具名输入和授权合同，不用假成功或占位 Provider 冒充真实业务。
- 当前销售 MVP 的终点是案管正式接收并形成稳定 MatterRef。紧接着的最小案管阶段增加“待分类 → 综法/执行/其他”；分案、承办团队、期限、办理和结案再按分类分批建设。已接收清单可先从转案事实只读呈现，实际可修改的案件分类由 Matter 领域拥有。
- 付款门槛存在需要显式处理的基线差异：当前冻结合同要求 ContractExecution、PaymentGate、DealActivated 在转案接收前成立。用户本次明确了销售/案管分类顺序，但没有单独决定所有合同的首款规则。**建议修订为签署/执行完成立即创建转案准备责任，收款跟进并行；只有具体合同明确约定到账后生效/允许转案时才阻断其接收。** 这是待纳入新业务合同的设计建议，不是已经取消现有守卫；必须同步定义激活条件、准确完成事实和守卫迁移，不能直接跳过 DealActivated 校验。
- MatterRef 当前要求 matter_type_code 和能力包版本非空。实施时必须区分“通用案件身份/接收能力”与“案管业务分类”：前者在接收时形成，后者在接收后由案管确认。若现行类型语义不能表达未分类接收，就通过具名合同和前向迁移扩展，不伪填为综法、不用 null 绕过原子槽，也不在分类时重新生成案件身份。
- 52＋2 是当前合同边界，不是永久禁止新增领域事实。字段/事实不足时明确升级合同、前向迁移和验证器；不把新事实塞进草稿、日志、审计摘要或任意 JSON 来保住表数。

## 6. 推荐实施顺序

| 批次 | 可交付结果 | 必须实现的内容 | 完成判据 |
|---|---|---|---|
| P0：开发基线收口 | 后续开发不再被 R1 总验收串行阻塞 | 当前状态表；开发准入与试点/发布门拆分；统一销售与签后转案边界、模板/角色范围；锁定依赖可复现 | 新开发可启动，R1 仍如实标记暂停/未验收；无业务成功伪造 |
| P1 / R2-A：导入与商机待办 | 销售能导入线索，首联后继续收到商机推进卡；主管看见责任和阻塞 | 导入预览/逐行回执；历史与新 OpportunityOpened 承接；商机参与方/进展/下一责任；最小业务台账 | 一条真实导入线索走到“商机进展已确认＋下一待办”，重新打开仍一致；重复输入不重复建档/建卡 |
| P2 / R2-B：材料与报价 | 销售完成报价，主管审批，客户回复进入系统 | Evidence 接收/下载；报价范围/价格/付款条款版本包；审批、交付和回复；P0-06～11 | 准确报价获准且发给准确收件人，接受/拒绝均有事实；拒绝或修订形成新的责任/版本 |
| P3 / R3-A：合同生成 | 系统生成可下载合同并完成审批/签署/执行记录 | PRE_CONTRACT 审查与 P0-12；版本化模板渲染；ContractRevision/签署计划/签名证据/Execution | 导出文件与批准的主体、金额、范围和版本一致；改正文使旧批准/旧内容签署不能误用 |
| P4 / R3-B：签后转案准备及收款跟进 | 签署/执行后出现转案准备卡，财务责任按合同并行或形成准确条件阻塞 | PaymentConfirmation 去重；按具名修订后的生效/付款/激活规则核验；TransferSnapshot 与材料清单 | 已签合同能进入转案准备；只有合同规定的条件阻塞正式接收，不因尚未分类阻断 |
| P5 / R3-C：案管接收闭环 | 案管退回、销售补正，最终获得唯一案件编号 | 独立 PRE_TRANSFER 审查；REVIEW_TRANSFER 的 ACCEPT/RETURN；P0-13～15；原子 MatterRef 和回执 | 当前叶快照被接收，案管原 Task 完成；重复提交不产生第二案件身份；旧快照无法越过补正链接收 |
| P6：试点与薄 AI | 一组角色能连续使用全链，AI 缩短填写时间 | 受控提取/摘要/材料缺项建议；来源提示和人工确认；最小报表；实际试点缺陷收口 | AI 关闭/失败时全部业务可完成；至少完成正常链和退回补正链，按角色核对结果 |
| P7：最小案管分类 | 已形成案件由案管分类后交给对应业务责任 | MatterCreated 幂等承接；待分类案件清单；分类决定及准确历史；综法/执行/其他后继责任 | 分类发生于案件创建之后；改分类保留历史和同一案件身份；不要求一次实现全部办理流程 |

AI 的文本提取可在 P2 后开展，但不得占用合同/转案关键路径。P7 可在销售转案闭环成立后、与试点及薄 AI 同一迭代推进，不以 AI 完成为前置。MVP 初期不做自由 Agent、多渠道营销平台、动态审批引擎、模板可视化编辑器、完整财务总账或全域案件系统。

## 7. 首个开发迭代的实施任务

## 8. 后续切片的关键工程限制

**材料和报价：** 先形成可引用的文件接收事实、可信对象版本和业务晋级，再用准确材料支持报价回复/签字/付款。报价的范围、明细、付款条款、参与方和批准均绑定不可变版本。先接一个实际渠道；若采用有证据的人工交付，应明确具名渠道及证明来源，不能把文件下载或销售单击等同于送达。ExternalAction 超时未知不能直接重发；真实 Provider 适配随业务接入，不另建通用集成平台。

**合同生成：** 第一版用随发布版本管理的已审核静态模板，填入当事方、服务范围、费用、付款和签署条件，生成可预览/下载的 DOCX/PDF。渲染和对象字节处理放在数据库事务外，提交时引用准确对象版本与 digest。批准针对准确 ContractRevision，内容变化后重新取得相应批准和签署。模板编辑器和多种合同自动协商均不属于第一版。

**冲突审查：** 签约前与转案前分别有准确范围/版本/参与方、独立 Review 和 Finding 决定；不得因同一客户以前通过过就跳过。没有冲突的正常路径也要有明确完成事实。

**财务：** 可以由授权财务人员根据真实付款凭证人工确认；仍需防同交易重复确认、核对合同版本和币种金额。按第 5 节具名修订明确哪些合同付款条件阻断接收，哪些只是并行收款责任。不得用零元付款伪造激活，也不得因为案件已创建而自动确认到账。

**转案：** RETURN 留下准确 ReturnItem；销售按要求生成完整后继 Snapshot，不能覆写旧快照。ACCEPT 锁定转案根与合同根，检查当前叶、具名修订后的执行/激活条件、终止状态、材料、独立冲突审查和接收授权，在同事务写接收决定、MatterRef、Task 完成和事件。签约版本终止或旧审查失效时不得接收。未完成综法/执行分类不能作为拒绝创建案件身份的理由。

**薄 AI：** 只提取资料、起草结构化候选、解释下一步和指出缺项；展示来源，用户确认后才走已有命令。缺少模型、超时或提取错误时可手工完成；不让 AI 审批、确认付款或接收案件。

## 9. 开发门与试点/发布门

| 阶段 | 必须满足 | 可以后置 |
|---|---|---|
| 持续开发 | 依赖已实现事实；当前切片编译与必要测试通过；租户/授权/幂等/事务完整性不被破坏 | R1 旧环境全量重验、等待真实日期、容量基准、所有浏览器边界遍历 |
| 受控试点 | 目标角色能登录并完成正常链及退回链；业务结果可核对；关键权限、版本、重复提交和文件引用正确；试点涉及的已知功能缺陷关闭 | 大规模容量目标、全渠道接入、高级运营报表 |
| 正式发布 | 汇总仍适用的 R1 遗留和新切片缺口，完成影响真实用户/数据正确性的验收及部署恢复检查 | 仅明确不属于发布范围的后续能力 |

R1 剩余项目不全部是非功能项，包含首联黄金链、代办/权限和功能分支。暂停的是本轮投入与串行开发前置，不代表永久取消其上线意义。每轮只验证新增切片和受影响回归；证据适用时复用，不因日期变化要求重跑全部历史测试。
