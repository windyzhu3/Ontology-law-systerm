# 线索录入人默认分配：补充设计

日期：2026-10-08。状态：待用户审阅；本文件不代表功能已实施。

## 1. 用户要求与成功标准

用户明确要求：独立线索分配权限可以由管理员以后配置；当前用户录入的线索，录入人默认可以分配。

本补充修改 R2.5 与 Linux v22 初始化设计中“人工分配必须事先解析独立 LEAD_ASSIGN 负责人”的部分，不修改其余冻结范围。

预期：丁启明以总所主任律师任职录入联系信息完整、无重复的新线索，即使系统没有任何 LEAD_ASSIGN 授权，也能保存成功；形成唯一分配待办，由该录入任职完成分配，随后接收销售获得首联待办。其他销售以自己的有效录入任职录入时，同样适用。

“录入人默认可以分配”解释为本人、录入时的准确任职、本人实际创建的线索。切换到本人其他任职不合并资格；身份管理员、主管、同部门其他人不会因此获得分配权。这是本设计为保持既有任职授权边界采用的解释。

## 2. 已核实的现状

- 当前本地海华库没有有效 LEAD_ASSIGN 授权、没有成功保存的业务线索。
- 完整线索录入进入人工分配时，AssignmentPolicy.unique 必须解析唯一获权任职；缺少负责人导致 SUPERVISOR_UNRESOLVED，事务整体回滚。
- 线索表没有独立的不可变录入人字段。来源与账号的配置绑定用于限制录入来源，但不能单独证明历史创建人。
- 首次成功 CAPTURE_LEAD 的执行槽、终态回执、事实事件和命令审计均不可变；回执包含准确结果事实，审计包含实际 Principal 与 Appointment。它们可通过准确命令关联建立创建证据。
- 分配权限还被工作卡、草稿、前置条件标签、命令提交和回执恢复校验。仅修改待办 Owner 会产生“有待办但不能操作”的错误。

## 3. 方案比较与选择

| 方案 | 影响 | 结论 |
| --- | --- | --- |
| 只依赖当前来源账号绑定推定创建人 | 配置变更可能转移历史资格；SERVICE 与旧部署也不能可靠区分 | 不采用 |
| 新增线索域不可变创建人事实 | 归属清晰，但需要新的数据库契约、迁移和 Linux 发布支持 | 本次不采用 |
| 由执行域和审计域提供窄读端口，联合验证首次成功创建证据 | 复用既有不可变事实，增加准确业务资格判定和读端口 | 推荐并作为本设计选择 |

不自动创建 LEAD_ASSIGN 全局授权、不制造对象授权记录。现有 DIRECT、DELEGATED、OBJECT、SYSTEM 路径语义不改；录入人分支使用当前任职的 DIRECT LEAD_CAPTURE 资格，加上本线索的创建证据和任务归属校验。规则名称为 CAPTURER_OWN_LEAD，仅用于线索人工分配及其附属读取、草稿、回执，不把 LEAD_CAPTURE 在通用授权器中解释成 LEAD_ASSIGN。

## 4. 创建证据与资格

### 4.1 可信创建证据

执行域只返回准确线索首次 SUCCEEDED CAPTURE_LEAD 的执行槽、终态回执与结果选择器；审计域只返回该命令唯一且通过摘要、租户、命令类型、结果和元数据一致性校验的实际 Actor/Appointment 与原录入范围。由受信业务策略组合，业务 Repository 不直接跨域扫描审计表。

须同时满足：结果事实为本线索的初始修订；源账号、来源记录摘要与线索一致；不可变事实链一致；实际主体为 HUMAN；原录入无代理；原实际任职对应原实际人员；证据在同一租户。NO_CHANGE、REJECTED、另一命令的回执、只有同名来源均不证明创建。零个或多个符合条件的创建证据均拒绝默认资格，不能取第一条。

内部端口不返回案情、联系人、凭据或审计正文给页面，不调用 ADM-07 审计查询界面，也不要求销售获得 AUDIT_READ。它只向受信策略提供必要的创建证据；不新增对外审计披露渠道。

### 4.2 每次操作的当前条件

默认资格要求：当前人员及录入时的准确任职有效、组织有效；当前 Actor 与原创建 Actor/Appointment 完全一致；无代理；该任职对原录入组织仍有 DIRECT LEAD_CAPTURE；线索仍处于可人工分配阶段；当前有效 ASSIGN_LEAD 待办归属于该任职；所提交草稿、任务和线索修订均准确。

对象级禁止规则仍先限后允；LEAD_CAPTURE 或 LEAD_ASSIGN 的适用对象禁令都不能被默认规则绕过。接收任职独立验证，不能由录入人资格替代。

任务归属、阶段、资格和证据必须在业务及身份围栏内复验，提交前再验证。注销、任职失效、撤销录入授权或组织变更不使历史证据消失，但会停止当前默认操作资格。

## 5. 待办路由与业务范围

对本次新建 HUMAN 线索：在当前可信录入事务中，已通过录入校验且确认为实际新建的 Actor/Appointment 作为待办归属候选；不等待尚未写入的终态回执。业务事实、唯一待办、事件、回执和审计原子提交。事务完成后的读取与操作必须使用已提交创建证据，不能沿用内存 Actor 或客户端声称的创建人。

人工分配阶段优先给符合条件的原录入任职。因此初次保存不依赖独立 LEAD_ASSIGN 任职的数量；以后管理员授予独立分配权限也不自动接管既有录入人的待办。独立获权人员操作其他线索仍须符合现有准确任务 Owner 与授权范围要求，本次不新增任意抢办、转派或批量接管入口。

SERVICE、无可信 HUMAN 创建证据的旧线索继续使用既有独立分配责任解析；缺少或歧义时关闭操作，不猜测历史人员。既有有效待办不批量改 Owner。不开展历史数据迁入或业务重建。

自动分配、重复核验、联系方式补全、路由缺口处理仍按已有规则。通过上述阶段后来进入人工分配时，可用完整创建证据解析原录入任职；这些阶段本身不获得默认分配规则以外的新权限。

原任职失效后的既有待办保留真实归属并关闭操作；本次不新增失效任职接管机制，不默默转给主任或主管。若恢复同一任职的合法资格，依现有阶段和版本重新判断。身份权限的后续配置不等同于任务责任转移。

接收销售候选依现有来源的 routingOrganizationRootCodes、有效任职与 SALES_CONTACT_OWNER 资格解析：一部来源限一部、二部来源限二部；总所来源按已有组织树可选择符合条件的一部或二部任职。不得任意选择其他部门、停用人员或只有管理资格的任职。

分配成功按既有链路产生 lead_assignment，完成原分配待办，生成接收任职的 CONTACT_LEAD 待办；保证唯一有效主责任。来源依然代表原录入来源，不改成接收销售。

## 6. 页面、命令与审计

保存成功沿用现有成功回执与后续事项入口；分配使用同一公共菜单和现有“我的待办”工作卡及草稿提交，不增加独立分配后台。

统一在工作卡可见性、动作可用性、任务/草稿前置条件、草稿保存、ASSIGN_LEAD 提交、接收候选查询、成功及拒绝回执恢复中使用同一资格策略。缺少独立授权但具备本人资格时，页面须显示可执行分配；非本人不得通过直接 API 或猜测 ID 获得同样操作。

准确绑定创建证据、本线索、当前任务/草稿和当前录入授权；默认分支的审计证据应明确记录 CAPTURER_OWN_LEAD、原创建命令/事实、原人员/任职、当前资格和接收任职验证。独立授权分支继续记录真实 LEAD_ASSIGN 依据，不伪造授权授予事实。审计失败或最终资格失败时整体回滚。

相同 CommandId 重试和相同来源记录 NO_CHANGE 不重复创建线索或任务、不覆盖创建人；跨人员重试不能继承原回执访问资格。分配后旧草稿不得重复分配，重复提交沿用准确回执规则。

新增的默认分支元数据需要独立版本与严格解析；已有审计摘要、回执元数据及已发生事实不改写，旧独立授权命令仍可按原规则恢复。

保存若仍被其他冻结前置条件拒绝，应显示安全且准确的原因，保留录入字段；不能把重复核验或补全失败误称为本人分配权限失败。

## 7. 数据库、初始化与发布约束

本方案不增加数据库表/列，不修改已发布 Flyway migration，不更改 v22 schema 版本。由既有不可变回执与审计证据完成判定；不往来源配置添加人员身份充当历史事实。

海华初始化继续保持独立 LEAD_ASSIGN 为 PENDING_ADMIN_ASSIGNMENT；17 人、20 任职、组织、密码及强制改密要求不变。说明文件应区分“本人录入默认分配”和“独立分配他人线索”。不补发主管或主任的全局分配权限。

实施若发现既有事实无法准确证明创建关系，停止该方案并说明证据缺口，重新审阅需要迁移的设计，不能临时用来源绑定降级绕过。

发布按正式 Linux 同 schema 流程，备份、隔离恢复证明、健康核验和入口切换均保留。更新现有本地海华环境，保留账号与数据；不重新初始化、重置密码或修改原合成验收库。

## 8. 必须验证的场景

1. 零 LEAD_ASSIGN：丁启明总所任职、两个部门销售分别录入完整无重复线索，保存成功并只有一个本人分配待办。
2. 原人员原任职通过 UI 完成分配；候选范围符合来源配置；接收销售出现首联待办、来源不变。
3. 他人、本人其他任职、管理员任职、代理、SERVICE 不能使用本人默认分支；原有独立授权分支回归通过。
4. 工作卡、详情、草稿、标签、候选查询、提交、回执的准入一致；直接 API、篡改任务/线索/证据和跨租户全部拒绝。
5. 任职或授权撤销、对象禁令、组织范围变化、接收人停用在最终复验中阻断；不留下部分业务事实。
6. 创建证据缺失、歧义、摘要不符、NO_CHANGE 冒领、来源重新绑定不转移资格。
7. 重试、重复提交、并发分配、业务阶段变化不重复任务或 Assignment；审计失败整体回滚。
8. 联系方式补全、重复核验、自动分配、旧独立授权任务与回执恢复保持原行为；从补全/核验进入分配的本人资格准确解析。
9. 空库海华初始化及既有本地同 schema 更新核验，不自动授予 LEAD_ASSIGN，不改变密码或原账号数据。
