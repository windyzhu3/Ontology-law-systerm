## 1. R2 的完成目标

一名销售可以从录入或导入线索开始，在系统中完成联系、商机推进、收费方案/报价、合同准备和签署；系统随后把转案责任交给案管，处理接收或退回补正，形成唯一案件身份。案件形成后，由案管完成综法、执行或其他业务分类。

主管、销售、合同审批人、冲突审查人、财务和案管都能看见自己需要处理的事项；主管能够查看授权范围内的业务台账、当前负责人、下一行动、截止时间和阻塞原因。

R2 验收以完整业务场景为单位：**能进入、能处理、能衔接、能等待和恢复、能追溯、能结束。** 有页面、能保存、单个 API 成功或测试数量增长均不足以判定闭环完成。

R2 不包括综法/执行业务各自完整的办理、执行节点、庭审、结案、财务总账、薪酬绩效等后续系统。

## 2. 统一业务链和待办衔接

正常主线：

```text
线索录入/导入
→ 去重、补齐和分配
→ 销售联系并确认有效需求
→ 商机推进和当事方/服务需求确认
→ 报价批准并获客户接受，或取得直接准备合同的准确授权
→ 合同准备、签约前冲突审查、审批
→ 签署材料和签署结果核验
→ 合同执行条件成立
→ 转案准备与提交
→ 案管审查、转案前独立冲突审查
→ 接收并生成唯一案件身份
→ 案管分类：综法 / 执行 / 其他
→ 销售收到转案结果，案管进入后续业务入口
```

已确认支持两条合同准备入口：报价批准/客户接受后进入，或者经准确授权直接准备合同。两条路径均需明确委托主体、事项、范围、费用和条款，并汇合到同一合同审查、审批与签署流程。直接准备合同的授权不替代合同审批或客户签署。

案件身份在案管审核接收后生成，随后分类。收款有独立责任；只有具体合同明确要求先到账时才阻断转案，不对所有合同统一设置首款前置。

| 场景 | 当前责任人 | 提交结果 | 下一责任或终点 |
|---|---|---|---|
| 线索资料缺失 | 来源负责人/销售 | 补齐准确资料 | 分配责任或销售联系 |
| 疑似重复 | 来源负责人/主管 | 确认关联或保留独立线索 | 继续分配/联系，不另起重复业务 |
| 正常分配 | 主管或确定性分配规则 | 确认唯一销售负责人 | 该销售收到首联待办 |
| 无合格负责人 | 主管 | 指定合格人或记录调配处置 | 恢复分配；异常必须可见 |
| 联系有效 | 销售 | 确认有效需求并形成商机 | 商机推进待办 |
| 未接通/疑似无效 | 销售 | 联系结果 | 按规则重试、等待或主管复核 |
| 商机跟进 | 销售 | 会谈、材料、需求或方案的准确进展 | 新的跟进责任或报价/合同准备 |
| 商机停滞/终止 | 销售/主管 | 处置结果和原因 | 继续跟进、调整方案或明确结束 |
| 报价待批准 | 有权审批人 | 批准/拒绝准确版本 | 报价交付或销售修改 |
| 报价交付与客户回复 | 销售/客户受控入口 | 有证据的发出、接受或拒绝 | 合同准备、报价修订或终止 |
| 直接准备合同 | 有权授权人 | 绑定准确商机、范围与收费方案的授权 | 合同准备；不伪造报价接受，也不跳过合同审批 |
| 合同资料不足 | 销售 | 补齐当事方、范围、条款和材料 | 生成合同或重新提交审批 |
| 冲突待处理 | 冲突审查人 | 对准确范围与 Finding 作决定 | 允许继续、要求补充或阻断 |
| 合同待审批 | 合同审批人 | 批准/退回准确合同版本 | 签署准备或销售修改新版本 |
| 合同待签署/核验 | 销售及授权核验人 | 签署证据、核验结果 | 执行条件核验及转案准备 |
| 收款待核实 | 财务 | 准确到账事实或核验未通过 | 满足合同条件，或继续收款跟进 |
| 转案资料准备 | 销售 | 完整转案快照 | 案管审核待办 |
| 案管退回 | 案管 | 明确逐项补正要求 | 销售补正待办 |
| 补正重提 | 销售 | 完整新快照及逐项回应 | 案管重新审核 |
| 案管接收 | 案管 | 接收决定和唯一案件身份 | 销售结果回执、案管分类待办 |
| 案件分类 | 案管 | 综法/执行/其他分类事实 | 对应后续业务入口；案件身份不变 |

## 3. 待办连续性的强制要求

1. **每个节点都有后继规则。** 每种提交结果明确产生哪项事实、结束哪张卡、交给谁、何时开始、何时到期；合法终点明确显示业务已结束。
2. **交接不能丢。** 原责任完成与本地后继创建保持原子性；异步衔接使用持久化事件和可靠消费。界面区分业务已提交、下一责任正在同步、同步失败，不能诱导重复提交。
3. **负责人不能悬空。** 离职、任职失效、授权撤销或没有分配候选时，进入主管可见的异常处置；不得悄悄停住。主管本身无法解析时，运营侧必须看到待修复项。
4. **重复不会多建。** 双击、重试、事件重复或乱序不能产生第二份进展、第二张同一责任卡或第二个案件身份。
5. **旧业务也能接续。** 历史有效首联已创建的商机要补齐首个推进责任；不能只有 R2 上线后的新线索可继续。
6. **等待有明确原因和恢复条件。** 包括下次联系时间、等待材料、等待客户、等待审批/签署/付款。到期处理使用可靠调度；不依赖用户刷新页面或开发者运行脚本。
7. **责任交给别人时正确结束原卡。** 等待其他 Owner/客户/外部服务从准确下游事实呈现；不把已完成的原人工责任无限挂为等待。
8. **退回、修订和转派有历史。** 形成新任务或新业务版本，旧任务不重开。转派必须保留原因与来源，并保证后续责任和授权正确。
9. **刷新或重新登录能继续。** 已保存草稿可恢复，已确认结果不丢，未知提交结果通过原命令回执核对。未保存输入在同会话切换前给出提示，不承诺把敏感正文长期留在浏览器。
10. **逾期会被看见。** 当前责任、期限、停滞时长、阻塞类型和超期责任进入主管列表；R2 默认先实现站内提醒。
11. **业务失败可处理。** 拒绝说明原因；可补正的问题给出下一行动；外部结果未知时不能直接重复发送/签署。
12. **完成依据是业务事实。** AI 输出、按钮点击、草稿保存、文件上传或 HTTP 200 都不能直接替代审批、签署、到账、转案接收。

## 4. R2 必须交付的业务功能

### A. 线索入口与销售建档

- 手工录入；CSV/XLSX 模板导入、字段映射、预览校验、错误行定位和结果汇总。
- 来源记录键和逐行幂等；成功行不重提，失败/未知行能按原记录恢复。首版批次规模设上限，不建设通用批处理平台。
- 复用 R1 去重、补齐、分配、联系和主管复核；增加真正面向用户的入口。
- 客户/当事方身份锚点与联系方式的授权读取及必要维护，不另建重复客户真源。

### B. 商机推进

- 有效联系自动进入商机推进待办，含历史商机接续。
- 确认参与方、需求、服务范围、进展依据和下一行动；记录跟进历史。
- 停滞、拒绝、失单和关闭有明确决定；需要继续行动时形成新责任。
- 界面阶段从业务事实计算，不允许通过直接修改“阶段”绕过责任和审批。

### C. 材料、收费方案与报价

- 文件上传、接收、版本、受控预览/下载、归属与材料清单；支持后续签字件和付款凭证引用。
- 报价范围、明细、收费方式、付款安排和有效期；版本化修改和权限内审批。
- 报价交付、客户接受/拒绝及对应证据；修改后形成新版本和后继责任。
- 首版只接一条实际交付路径；可以是经确认的人工交付留证，不用“下载成功”冒充客户已收到。

### D. 合同准备、审批与签署

- 使用已审核模板生成可预览/下载的合同；填写委托主体、事项、服务范围、费用、付款与签署要求。
- 合同模板首版随版本管理，不建设可视化模板编辑器；案管业务分类不作为签约前置。
- 签约前冲突审查、合同审批、退回修改和再次提交。
- 签字件上传、签署核验、必需签字/盖章/归档条件核验及合同执行事实。
- 第一版可使用人工签署证据路线；电子签集成不是默认前置。正文变化后旧批准和旧内容签名不能被误用。

### E. 收款与转案

- 财务根据可信凭证记录到账；按交易和事实类型去重，核对合同归属、币种、金额与准确版本。
- 按已确认规则判定收款是并行责任还是接收条件：只有合同明确要求先到账时阻断接收。
- 销售提交完整转案资料、签署合同和已确认业务信息；案管拥有审核、退回和接收入口。
- 退回逐项列清补正要求；重提形成完整后继快照；只允许接收准确当前版本。
- 接收原子形成唯一案件身份、完成案管审核责任，并向销售显示转案结果。

### F. 案件形成后的最小管理

- 待分类案件列表和详情，关联原线索、商机、合同及转案材料。
- 案管将案件确认为综法、执行或其他类型；保留分类历史，改分类不换案件编号。
- 完成分类后有明确的承接人或业务入口；完整各类办理流程后置。
- 若需新增 Matter 领域表，正式升级字段合同和迁移；不把可变案件档案塞进转案快照。

## 5. 配套管理功能

| 管理区域 | R2 必需能力 | 边界 |
|---|---|---|
| 用户、组织、任职、授权 | 复用已实现四页；补足新销售、审批、财务和案管权限；有效负责人维护 | 不建设 HR/薪酬体系 |
| 来源与分配 | 查看来源、导入结果、分配状态；人工指定/受控转派；负责人异常处理 | 先使用受控来源配置和固定规则，不做动态规则编排 |
| 客户与线索台账 | 搜索、来源/负责人筛选、联系状态、关联商机和处理历史 | 不给用户跨租户或跨授权范围的全局视图 |
| 商机与报价台账 | 当前进度、最近联系、下一行动、停滞原因、报价版本和客户回复 | 不支持跳过业务命令的任意“改阶段” |
| 合同台账 | 合同编号、版本、审批/签署状态、原文件和关联业务 | 不由后台直接改为“已签署” |
| 收款台账 | 待核实/已确认金额、凭证、合同条件、待跟进记录 | 不扩展总账、发票、税务、分润 |
| 转案与案件台账 | 待提交/待审核/退回/已接收/待分类；材料缺项和案件身份 | 不把“已转案”误称为后续办理已完成 |
| 团队待办与异常 | 我的待办、团队待办、等待、逾期、无负责人、失败衔接、受控恢复 | 不能直接勾选完成任意任务；所有恢复须守授权和因果 |
| 操作与审计查询 | 查看谁何时确认何项业务、准确版本、退回/转派原因 | 不将敏感正文复制进审计或通用日志 |
| 最小经营概览 | 线索数、有效商机数、签署数、转案数、待办逾期数；可追溯到台账 | 先统一统计口径，不做复杂 BI/绩效排名 |

普通用户继续以当前工作卡为主要操作入口；同一应用提供授权内的台账/团队查询和业务详情。保留系统推荐当前事项，同时允许从“我的待办”主动切换其他有权处理的事项；同一时刻只展开一张完整工作卡。选择事项不改变负责人、任务状态、期限或业务优先级，不取得额外权限。读取和提交均由服务端重验当前权限与任务可处理性。

### 管理页面与工作台的强制设计约束

设计沿用[既有工作卡基准](../../design/sales-mvp-workcards/README.md)和[既有管理界面基准](../../design/identity-admin-mvp/README.md)。R2 扩展本节已确认的业务管理能力，复用既有视觉和交互，不重新设计整套应用。旧身份管理基准的业务范围仍约束身份页面，不据此取消已确认的 R2 业务台账。

1. **保持同一入口。** 使用同一 SPA、统一顶栏与受保护的管理模式。普通工作台通过轻量“我的待办”列表或侧面板选卡，不另建一套普通用户模块导航；管理区沿用管理侧栏和响应式内容区。
2. **保持既有风格。** 复用现有设计 tokens、组件、字体排版、间距、表单、表格和按钮样式。暖白背景、石墨文字、翡翠绿唯一主强调色、浅薄荷辅助色、1px 边框与弱阴影保持一致，不引入第二套主题。
3. **保持操作简单。** 工作卡只承载一个负责人、一个业务目的和一个固定主命令；可操作管理页仅一个视觉主操作，只读页不强造主操作。筛选、查看详情、切换事项等次要动作不能与业务提交竞争。
4. **按需展开信息。** 默认只展示当前决策必要的字段、状态、负责人、期限、阻塞原因和下一行动；低频字段、历史、更多筛选按需展开。十类管理能力不等于强制新增十套独立页面，不重复建表单或增加多层导航。
5. **切换不中断业务。** 草稿按事项隔离，保存后可恢复；未保存输入切换前明确提示并允许取消。提交进行中或回执未知时禁止重复提交，并可核对原结果；切换不能把未知结果当失败重做。失权或已被处理的事项说明原因并返回可处理列表。
6. **使用业务语言。** 不向用户暴露 UUID、表名、内部枚举或技术修订号；沿用既有加载、空态、错误、等待、成功和只读反馈方式。普通切换和查看不增加确认弹窗，重要业务操作沿用已有确认模式，避免连续弹窗。
7. **AI 融入原流程。** 候选字段、摘要和缺项建议出现在对应表单或材料区，标明来源与“待人工确认”；可编辑、采纳或忽略，不新增必须经过的 AI 对话步骤。
8. **沿用可用性基准。** 保持响应式布局、键盘可操作性、标签及焦点反馈；每个工作包核对受影响页面与既有卡片/管理页面的一致性，并演示正常、空态、异常和恢复路径。只验证本次改动，不启动无边界的视觉重做。

## 6. 实施工作包与每包验收

| 顺序 | 工作包 | 完成时必须能演示 |
|---|---|---|
| R2-0 | 一次性确认范围、后继合同与开发准入 | R1 暂停保留；新开发可启动；不把准入修订当业务完成 |
| R2-1 | 线索入口＋历史/新商机接续＋首个推进卡 | 导入 → 首联 → 商机卡 → 确认进展 → 下一待办；主管看见责任 |
| R2-2 | 商机推进/关闭＋客户资料＋团队管理＋主动选待办 | 跟进、停滞、转派、等待、主管处置都能继续；授权内切换并恢复草稿；台账与事实一致 |
| R2-3 | 材料接收＋收费/报价及客户确认 | 准备 → 批准 → 交付 → 接受/拒绝 → 合同准备或修改待办 |
| R2-3 内的双入口 | 直接准备合同的具名授权 | 销售发起 → 有权人确认准确范围/条款 → 合同准备；与报价接受路径汇合，仍执行合同审批 |
| R2-4 | 合同生成＋冲突审查＋审批签署 | 可用合同文件 → 审批 → 签署核验 → 合同执行 → 转案准备 |
| R2-5 | 财务确认＋转案审核/退回/补正/接收 | 条件核验 → 提交 → 退回补正 → 接收 → 唯一案件身份和销售回执 |
| R2-6 | 建案后分类＋管理收口＋三项 AI 辅助收口 | 待分类 → 确认类型 → 正确承接入口；各台账/异常/统计可用；字段提取、跟进摘要、缺项提示均可人工确认 |
| R2-7 | 完整业务试点与验收 | 多角色连续完成正常链及关键异常链，清楚列出剩余范围外项 |

管理页面随对应业务工作包交付，不全部堆到 R2-6。每包包含必要的模型、命令、读接口、前端、角色权限、测试与演示，避免“只交后端”或“只有静态页面”。

三项 AI 辅助随线索/材料、跟进、材料核验场景接入，在 R2-6 统一收口；不能以人工流程可用代替三项 AI 功能交付。各包均遵守第 5 节设计约束。

R2-1 首要代码落点：OpportunityOpeningService 的下游承接、TaskFactory/Task 查询的准确 Subject 扩展、CurrentWorkCardQuery、草稿与命令/事件静态注册、同一 OpenAPI 和工作卡前端。再接入导入入口与查询，避免录入更多线索后仍然停在商机锚点。

## 7. 必须在实施计划中解决的现有设计缺口

- 现有 TaskFactory、卡片查询、草稿校验和授权主要针对 Lead，不能只增加几个 taskType 字符串就认为支持全销售链。
- opportunity_progress 目前主要保存类型、摘要、准确来源和时间，不具备完整跟进正文存储；需明确受保护的事实来源或前向字段修订。不能把已确认跟进记录只留在 ActionDraft。
- 历史 OpportunityOpened 可能已被 R1 消费；要单独设计有界回补与新事件衔接，幂等依据必须持久化且能抗并发，不能改写旧 R1 Outbox 状态凑接续。
- 全链工作卡需要相应的 Owner 读取、披露审计、提交前重验和失败恢复，不允许靠管理查询直接跨域修改事实。
- 当前合同锚点依赖准确的已接受 QuoteIssue；用户已确认支持“直接合同”，需要正式增加合法来源与授权合同，不创建假报价或假客户接受。直接授权必须绑定准确商机与条款范围，不能成为跳过合同审批的捷径。
- 当前转案前要求执行/激活事实；付款规则改变时同步修改激活判据和检查，不直接删除守卫。
- MatterRef 的非空类型/能力包与“创建后分类”需要区分通用接收身份和业务分类，不预填为综法，也不在分类时创建第二案件身份。
- 全链未来出现更多补正/转派/等待时，必须采用明确责任类型及版本规则，不能发展成无边界的通用流程引擎。

## 8. 已确认决策与范围控制

以下决策已经用户确认，是后续细化的固定输入；实现时仍需正式修订对应合同与守卫。

| 编号 | 决策 | 用户确认结果 | 对计划的影响 |
|---|---|---|---|
| Q1 | 正式报价是否必经 | **已确认：** 保留报价，同时允许授权后直接准备合同 | 修订合同来源为明确的报价接受或直接授权路径；不得创建假报价/接受 |
| Q2 | 案件在何时生成 | **已确认：** 案管审核接收后生成，再分类 | 保留接收时原子形成唯一案件身份；分类为后续案管责任 |
| Q3 | 首款是否阻断接收 | **已确认：** 按合同约定，只有明确要求先到账的合同才阻断 | 收款通常为并行责任，具备明确条件时阻断；同步修订激活判据 |
| Q4 | 是否允许主动选待办 | **已确认：** 系统推荐之外，可从“我的待办”切换其他有权处理的事项 | 修订当前卡选择契约；单卡展示、逐次鉴权、草稿保护与回执恢复保留 |
| Q5 | R2 AI 范围 | **已确认：** 字段提取、跟进摘要、材料缺项提示，全部人工确认 | 三项均须交付；AI 输出为候选，不能自动成为业务事实 |
| Q6 | 设计与范围约束 | **已确认：** 简单易用，与既有卡片及管理界面一致；不随意扩围 | 第 5 节作为各工作包设计与验收约束；范围变更单独确认 |

以下配套边界纳入本次确认范围：

- **待办选择：** 按 Q4 和第 5 节实施，不把“推荐”实现为强制顺序，也不放开无权限任务。
- **转派：** 主管可以受控转派未完成责任，形成新卡并保留历史；销售不能任意转给无权限人员。
- **提醒：** R2 默认站内等待/到期/逾期提醒和主管异常列表。短信、企业微信、邮件提醒不是默认前置。
- **AI：** 从用户有权访问的线索/材料提取候选字段、依据跟进记录生成摘要、按当前材料要求提示缺项。保留来源，允许修改或忽略；人工确认后仍通过原业务命令提交。缺项建议不替代确定性必填/准入检查；AI 不可用时支持手工完成。不得自动审批、确认签署/到账、接收转案或自主执行后续命令，不建设全自主 Agent。
- **签署：** 首版实现人工签字件上传和授权核验；真实电子签集成不在本次默认范围内。
- **管理范围：** 默认包含第 5 节十类最小能力，不包含完整案件办理、财务总账、绩效和薪酬。
- **责任人配置：** 首版明确销售主管、销售、直接合同授权人、合同审批人、冲突审查人、财务、案管和系统管理员的职责；允许同一人拥有多个合法任职，不自动获得其他职责的权限。具体审批人/金额权限在试点配置中确定，不先建设动态审批设计器。

每个开发任务必须对应本文的工作包、业务场景和验收项。实现已确认范围所需的接口细化、迁移、错误恢复和测试可直接推进；新增业务模块、扩大 AI 自动执行权限、引入范围外外部渠道、通用流程/模板/审批平台或整体 UI 改版，必须先记录变更内容及对交付的影响，并单独取得用户确认。不得以技术优化或顺便完善为由扩围。保留现有系统架构、权限、事实不可变性和设计约束，仅对本次已确认冲突做具名修订。

## 9. R2 最终验收清单

- [ ] 报价成交链：新线索 → 商机 → 报价批准/客户接受 → 合同签署 → 转案接收 → 唯一案件身份 → 分类。
- [ ] 直接合同链：新线索 → 商机 → 准确直接准备合同授权 → 同一合同审批/签署链 → 转案接收。无报价接受记录仍能合法完成；无直接授权则拒绝。
- [ ] 历史接续：R1 已形成的有效商机能进入 R2，不重复建档或补造联系事实。
- [ ] 线索异常：重复、资料缺失、无合格负责人均能进入明确处置并继续或结束。
- [ ] 跟进等待：预约联系/补材料到期后正确恢复；逾期主管可见。
- [ ] 商机异常：停滞、失单和关闭有准确结果，不留下不应存在的普通跟进卡。
- [ ] 报价/合同退回：拒绝或修改形成新责任和新版本，旧批准/旧签名不能错用。
- [ ] 外部结果未知：恢复原结果，不盲目重复交付或签署。
- [ ] 财务异常：重复凭证/交易不重复确认；合同要求先款且未到账时阻断，没有先款约定时不因未收首款阻断；建案不自动确认到账。
- [ ] 转案补正：案管 RETURN → 销售逐项补正 → 重提 → 接收；旧快照不可接收。
- [ ] 权限与转派：负责人失效、授权撤销、主管转派可见且能受控处理，不能越权操作。
- [ ] 刷新与恢复：重新登录/刷新/提交确认丢失后可恢复原草稿或原结果，不重复业务。
- [ ] 管理一致：台账、经营数字、当前责任与准确业务事实一致，并受权限范围限制。
- [ ] 主动选待办：系统推荐和手动选择均可用；只能处理授权事项，始终单卡展示，切换不丢已保存草稿、不串数据、不重复提交。
- [ ] 三项 AI 均可演示：字段候选、跟进摘要、缺项提示有来源且可人工修改/确认/忽略；未确认不成为业务事实；AI 失败时仍能手工完成全链。
- [ ] UI/UE 一致：受影响卡片与管理页面复用既有风格和交互，主操作明确、低频信息按需展开，等待/失败/切换均有清楚反馈。
- [ ] 范围可追溯：交付项对应已确认工作包；新增范围有单独确认记录，无未经确认的新模块或整体改版。

每个工作包执行受影响的单元/契约/真实数据库测试和具名浏览器场景；最终完成一轮多角色全链演示。R1 已有适用证据复用，暂停项不被伪记通过，也不要求无差别重跑全部历史验收。
