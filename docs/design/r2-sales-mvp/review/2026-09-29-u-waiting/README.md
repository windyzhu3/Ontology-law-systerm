# U：工作卡下方“我的等待事项”补稿

状态：用户已确认，功能实现及本地验证完成。日期：2026-09-29。

## 目标与边界

在现有工作台的工作卡下方补齐本人等待事项的查看入口。用户能知道在等什么、何时或何种条件满足后继续；查看不丢失当前填写。沿用当前主分支公共身份及按钮样式，复用 S 补稿的只读记录表达，不新增一级菜单、管理权限、第二套业务表单或强制唤醒操作。

## 页面与交互

- 默认收起；按钮为“等待 N 项 · 查看等待事项”，展开后为“等待 N 项 · 收起”。查看和收起只改变该区域，不替换工作卡，不改变路由，不自动滚动到页首。
- 一行显示客户/业务、事项名称、等待原因、约定时间或下次核对时间和状态。最多先读取一页，显式加载更多；数量为完整有权集合总数，不是当前已加载行数。
- 点击行就地展开只读详情（同时一个），包括本人任职、状态、原因、时间、下一步和可展开的最近记录。窄屏仍在原行下展开；操作目标至少44px。
- 未到约定时间、等待条件满足、已到核对时间分别表达。已到核对时间不自动等于逾期或责任异常，也不能在客户端自动切成可办理。
- 服务端确认可办理且当前任职仍有办理权后，移出等待计数；若正在查看该项，短暂保留带“已可办理”说明的详情，提供“前往办理”。因此短暂保留行不计入等待总数，须明确说明。
- 前往办理前重读准确任务及授权。若有未保存内容，沿用原“继续填写 / 放弃并前往 / 可保存时保存草稿并前往”；保存失败或结果未知时留在原卡核对，禁止导航。原型只模拟保存成功分支。
- 点击时已变化或失权：移除旧详情、撤下办理入口，提示重新读取；不依靠旧列表中曾经出现的按钮授权。
- 无当前可办理工作卡时，等待区域仍可独立查看。总数为0时显示空态；读取失败、权限变化不能伪装为0或“全部完成”。原型加载/错误数量以“—”表示未核对。
- 当前业务提交中或原结果未知时，等待读取不得影响原请求；“前往办理”服从现有阻塞状态。

## 正式实现约束

当前 waitingCount 来自 CurrentWorkCardSources 中当前本人/代办任职的有权 WAITING 集合。正式列表、详情、总数必须复用同一责任范围及逐对象授权；不能把团队接口直接开放给普通办理人，也不能拿 nextSummaries 代替等待明细。

只读查询要包含可安全展示的业务标题、等待原因、约定/核对时间、当前等待状态、记录摘要与准确任务标识。可办理资格必须服务端重验，不由客户端比较时间推断。所有时间按北京时间展示，缺少核对时间明确显示“尚无约定核对时间”。分页采用稳定顺序，建议已到核对时间优先，再按下一核对时间、稳定标识排序。原型的固定行顺序用于演示，不作为正式排序算法。

总数与列表需来自同一授权和一致性口径；身份变化清空旧缓存，撤权不泄露旧客户信息；响应迟到不能覆盖新任职或新查询。正式缺少个人等待列表查询，应补只读契约及后端投影，不能仅把数字改成前端按钮。

## 评审与验证

入口 index.html 可切换13个场景及桌面/390/360宽度。app.html 为实际演示页面。全部使用合成记录、无业务接口调用；当前工作卡提交与页头按钮为背景参照。

三种宽度共39项布局检查；交互检查输入保留、收起/展开、详情展开、未保存拦截、模拟保存后进入原卡、点击时失权清空、失败重试及加载更多。结果见 review.json；检查脚本见 review-check.js。人工查看桌面详情与360px到期等待截图。CSS来源与SHA256见 shared-style-sources.json，复制文件不作变更。

本补稿不代表产品功能已经实现，也不改变 R2.5 业务验收结论。确认后再实施个人等待查询和工作台入口。
