# Task9 人工验证执行计划

状态：用户已确认手工验证完成并要求关闭，人工操作待办已关闭；见[用户签认记录](task9-real-user-uat-template.md)。实际执行时间、账号别名和构建信息待补充归档。本计划保留为原步骤说明，不重新启动开户、授权或人工操作。

## 目标和边界

由本任务用户本人实际登录、办理一张责任卡、体验资格暂停及恢复。管理员与使用者采用两个独立浏览器配置文件，避免SSO串号。只使用本地合成资料；不得把代理自动操作或既有六卡／等待自动证据当成人工确认。

入口：[登录](https://localhost:19444/login)、[工作台](https://localhost:19444/workbench)、[身份管理](https://localhost:19444/admin/identity/principals)。这些是既定本地地址，执行前须重新核验服务和证书；本文不声称当前服务健康。

附件上传、通知、语音、ADM-05～07、容量压测均不进入本次人工验证。

## 开始前的准备门（协调者／获授权管理员，预计15～20分钟）

1. 用户确定实际执行时间。期间暂停对同一测试身份和责任的自动业务写入；不暂停正常Worker、不改时钟。
2. 记录实际buildSha、environmentDigest、日期、使用者及管理员别名。若制品已变，不能沿用旧构建结论。
3. 确认API／SPA／Worker和Keycloak可用，原CA可信。若出现证书警告、账号来源不明或业务身份不符，停止，不能跳过校验。
4. 推荐使用一套专用UAT身份及受控测试组织，避免改动原四个自动验收账号、原15命令和5命令检查点。开始前须明确确认新账号别名、组织、任职、授权范围及管理员操作者，再按受控入口创建。此前仅用于Keycloak建号测试的新增账号不自动收养为UAT账号。
5. 凭据只在本机受保护文件或Keycloak受控设置流程中交付，用户自行输入；不写入本计划、聊天、Git、截图或验收报告。Keycloak用户管理员只管理外部账号，不替代业务系统的身份管理员。
6. 通过真实API准备一条独立、可识别的合成MANUAL线索，再由已有获权主管经页面分配给UAT首联任职；不得直接插Task、改Owner或改数据库。准备动作另存证据，不冒充使用者本人完成。
7. UAT开户和业务准备具体目标未确认前，本计划只可阅读，不可据此批量建号／授权。若专用组织的责任范围不满足实际候选规则，应先调整准备方案，不默认扩大到根组织授权。

## U01：受控开户与取得资格（用户观察并确认，预计10～15分钟）

| 步骤 | 操作 | 应看到／应确认 |
|---|---|---|
| 1 | 获授权运维在local-r1准备明确的UAT账号及初始凭据 | 账号属于准确realm，不使用原管理员或真实客户资料 |
| 2 | 业务管理员进入ADM-01，输入完整用户名精确查询，选择准确候选并建立本地身份 | 不按姓名／邮箱猜测、不手填subject、不自动开户 |
| 3 | ADM-02建立已确认的测试组织；ADM-03建立首联经办CONTACT_OPERATOR任职，核对组织和任期 | 岗位与权限分开；未授权时不能办理首联 |
| 4 | ADM-04授予SALES_CONTACT_OWNER，核对任职、静态权限、批准范围和有效期 | 仅最小业务授权；不赋予管理权限或其他业务权限 |
| 5 | 用户在自己的浏览器登录并核对显示的本人／组织／任职 | 实际身份正确；管理员资格不冒充业务责任Owner |

用户确认语句：`U01：账号与任职正确，组织／授权范围已核对，通过／不通过（现象）。`

## U02：本人办理责任卡（用户操作，预计10～15分钟）

1. 用户自行打开工作台，登录后选择准确任职。核对今日摘要、当前首联卡、后续摘要和等待数量；最多一张完整当前卡。
2. 输入本次指定的合成首联内容，采用EMAIL及NOT_CONNECTED。保存前观察主提交限制；点击保存候选后，确认“已保存”不代表业务已完成。
3. 修改一处尚未保存的字段，确认主提交不能直接执行；再次保存后，明确点击一次业务确认按钮。
4. 等待结果反馈，不双击或反复提交。正常结果应为首联结果已记录、当前卡退出，出现仅等待状态；等待数以本次服务端结果为准，不沿用旧测试数量。
5. 点击“刷新当前责任”，再整页刷新并通过已有SSO重新进入。确认身份和等待状态正确，没有重复责任或重复业务结果。
6. 协调者只读核对原命令、Receipt、ContactResult、Task及WaitReceipt，记录真实恢复时间。不修改等待期限，不要求用户等到下一工作日才能确认本项。

用户确认语句：`U02：本人完成保存和一次提交，刷新后状态正确，通过／不通过（现象）。`

## U03：资格暂停、恢复与退出（管理员配合用户，预计10～15分钟）

推荐选择可逆的“暂停任职／恢复任职”，属于原U03允许的挂起路线；不使用不可逆禁用、结束任职或撤销Grant冒充可恢复操作。

1. 用户保持工作台打开；管理员核对准确UAT任职后，在ADM-03点击“暂停任职”，检查影响与原因后二次确认。
2. 用户点击刷新，确认原任职失效，不能继续办理、保存或提交；旧内容不得继续作为有效可操作责任显示。Keycloak仍能登录不等于有业务任职资格。
3. 管理员对同一SUSPENDED任职点击“恢复任职”，确认成功。用户重新登录／重新选择准确任职，系统应重新验证任期和Grant；原等待责任不应消失或变成已完成。
4. 用户主动退出，检查页面敏感内容清除；浏览器后退、重新聚焦旧页面不能恢复可操作的旧会话。若IdP退出失败，应如实显示限制，不能声称全局退出成功。
5. 协调者核对暂停／恢复回执与审计、责任Owner和业务事实保持。若未来改验“撤销授权”，必须另列新授权步骤；已撤销Grant绝不能恢复成ACTIVE。

用户确认语句：`U03：暂停后不能办理，恢复后重新获权，退出后旧页面不可用，通过／不通过（现象）。`

## 失败处理和证据

- 任一结果未知时，停下并保留原页面／运行编号；不要换账号继续写、清理恢复标记、重新建卡或重发新key。由协调者查询原回执并判断下一步。
- 记录安全现象、发生时间、构建和用例ID；不收集密码、Token、subject、HMAC、原始请求正文或未脱敏DOM。截图仅在确有必要且不含上述信息时另行安排。
- 使用[人工记录模板](task9-real-user-uat-template.md)，逐项填写真实时间、用户确认和脱敏证据位置。首次失败保留，后续重验另记，不能覆盖失败历史。
- 人工操作约30～45分钟，另加准备与证据核对；实际以账号准备及故障处理为准。U01～U03全部由用户实际确认后才通过，不能因交付本文而勾选。
- 完整Task9还要求同最终构建自动必需项和独立评审完成。Task10／参考容量和R1上线另行判断。
